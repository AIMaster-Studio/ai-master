## ① 项目背景与痛点问题

### 1.1 先看一个具体场景

一名学生在视频平台看完一集四十分钟的大模型入门课。视频讲得很清楚，他一路点头，关掉播放器。

三天后，同学问他：检索到的资料是怎么进入模型回答的？他说："就是先查一下，再让它答。"

再往下问：查到的内容是以什么形式交给模型的？如果检索结果本身是错的，它会告诉你吗？——他停住了，说："这个我得回去再看看。"

**他不是没看过，也不是不努力。他是从来没有被要求把这些话自己说一遍。**

这个场景不是我们虚构的。在本次调研中，学生填写的困扰里最集中的一句原话是：**「概念抽象，没人帮我判断是否真的懂了」**。注意这句话的重点不在"抽象"，而在后半句——**没有人来判断**。看完教程之后，学生手上没有任何反馈：他不知道自己是真懂还是只是眼熟。

### 1.2 痛点从数据里来

本项目在 2026-09-06 至 09-08 收集了 **20 份匿名在线问卷**（n=20，探索性样本，未做统计推断；**项目自测，非第三方背书**）：

| 问卷结论 | 份数 |
| :--- | :--: |
| 认可「能讲清楚 ≈ 真正学会」 | 17 / 20 |
| 愿意使用「讲解自动判断」 | 16 / 20 |
| 认可"讲解通过 + 测验达标"双条件通关 | 14 / 20 |
| 已有「用自己的话讲一遍」的习惯 | 13 / 20 |

这里有一个值得注意的落差：**17 人认可"能讲清楚就算学会"，但只有 13 人真的会主动讲一遍。**
认可与行为之间的这 4 人差距，就是本作品要解决的问题——**学习者认同"开口"有用，但缺少一个逼他开口、并且能给他反馈的对象**。

需要说明的是：n=20 是探索性样本、非随机抽样，它只能说明"这个困扰在这批受访者中存在且集中"，**不能推断总体比例**。

### 1.3 现有三条路径，各缺一块

学生今天并不缺学习材料。缺的是**判断**。三条主流路径各自解决了问题的一部分：

| 现有方案 | 能给你什么 | 缺了什么 |
| :--- | :--- | :--- |
| B 站 / 慕课教程 | 讲解很完整 | **无法判断你是否真的懂了** |
| ChatGPT / 通用助手 | 替你说出答案 | **学生没开口 → 浅层学习的错觉** |
| 传统刷题 | 分数客观 | **只考记忆不考理解，背题即可通过** |

三行合起来看，缺口是同一个：**没有任何一条路径要求学习者先表达，再验收。**

第二行尤其值得展开。通用助手的能力很强，但它越流畅，越容易制造一种"我已经懂了"的错觉——因为**说出正确句子的是模型，不是学生**。学生做的是"读一遍并点头"，这恰好是浅层学习最典型的形态。

第三行的问题在于判据：客观题能测"记得住吗"，测不了"讲得清吗"。而现实里的表达任务——汇报、答辩、面试、把方案讲给同事听——**没有一道是选择题**。

### 1.4 本作品的立论

> **问题不是「没有内容」，而是学习者从来没有被要求真正表达一次。**

AI Master 要求学习者先用自己的话解释概念，再接受独立客观测验。当前六阶段的 33 个知识节点各自记录学习、讲解、测验与复习状态；节点通关表示满足原型规则，不代表长期掌握。

一句话概括本作品的立场：**先开口，再验收。**

## ② 需求分析：目标用户与功能需求

本章不列功能清单，而是给出一条因果链：**目标用户是谁 → 他们要完成的任务是什么 → 因此需要哪些功能。**

### 2.1 目标用户是谁

**主用户：正在学习大模型与 RAG 入门知识的高校学生。**
使用场景是课程实践或自主练习，不是考证、不是求职突击。他们的时间被课程和作业切得很碎，能投入的通常是每天三十分钟到一小时。

**次用户：任课教师。**
教师的需求不是"再要一个后台"，而是**低成本发现班级里哪个概念被反复讲错**。需要明确的是：教师班级视图与概念错因汇总属于后续产品范围，**当前原型没有交付**，本章只把它作为需求方向记录。

### 2.2 他们各自要完成的任务

把"用户"换成"任务"，需求才立得住。四件事：

| 用户 | 要完成的任务 | 今天的实际做法与卡点 |
| :--- | :--- | :--- |
| 学生 | **确认自己是不是真的懂了** | 重看一遍视频、翻笔记——但"再看一遍觉得懂了"与"真的懂了"不是同一件事 |
| 学生 | **知道具体哪里没懂、下一步补什么** | 卡住时只能问同学或搜关键词，得到的答案往往又是另一段需要判断的材料 |
| 学生 | **留下可复查的学习过程** | 过程散在视频进度条、笔记和搜索历史里，学期末无法回看"我当初是怎么错的" |
| 教师 | **发现被反复讲错的概念** | 收作业、批改、归纳，成本高，且多数练习是客观题，看不出表达层面的问题 |

### 2.3 从任务推出功能需求

| 任务 | 由此产生的功能需求 | 本作品对应功能 |
| :--- | :--- | :--- |
| 确认是否真懂 | 需要一个**无法靠"看"通过的验收动作** | 讲解提交 + 结构化复评 |
| 知道哪里没懂 | 反馈必须**指出具体缺口**，而不是只给分数 | 带来源标注的即时反馈、七项检查明细 |
| 留下过程 | 记录要**可保存、可导出、可回看**，并说清数据所在位置 | 本机模式使用 SQLite 或 localStorage；公网页面与远程 API 按实际配置使用独立后端存储 |
| 验收要可信 | 讲解与测验两个条件**都必须独立满足** | 双条件通关（讲解通过 + 客观测验 75%） |
| 教师发现问题 | 需要按概念聚合的错因视角 | 属后续产品范围，当前未交付 |

**这张表里最关键的推论在第四行**：如果验收只靠一种判据，学生就能针对那一种判据取巧——只刷题就背题，只写作文就套模板。所以**本作品使用两种性质完全不同的判据**，并且**分别计算、互不代偿**。

### 2.4 明确不做的四件事

需求分析的另一半是划掉不做的部分：

1. **不做内容分发。** B 站与慕课已经把"讲解完整"做到了极高水准，本作品不与之竞争。
2. **不做通用问答。** 通用助手在开放问答上更强，本作品不重复这一能力。
3. **不替学生作答。** 任何"直接给出答案"的功能都不做——这正是本作品要对抗的学习形态。
4. **当前不做班级管理与教师后台。** 没有试点数据支撑之前，不做这类功能。

## ③ 开发工具与运行环境

| 层 | 工具 / 技术 | 用途 |
| :--- | :--- | :--- |
| 运行时 | **Node.js 24**（内置 HTTP 服务） | 后端服务，不引入 Web 框架 |
| 数据存储 | 本机模式为 **SQLite**；静态回退为 localStorage；公有后端可配置远程 Turso | 各部署形态分开说明，不能概括为“所有数据都留在本机” |
| 前端 | **原生 HTML / CSS / JavaScript** | 无构建步骤，页面可直接打开 |
| 可视化 | 星图交互（知识星海） | 概念关系呈现 |
| 桌面入口 | **Electron** | 除 Web 工作台外的第二条入口 |
| 公网形态 | Cloudflare Pages + `_worker.js`，将 `/api/*` 代理到独立 Vercel 后端 | 以仓库部署文档与现场探测为准；不再描述为“公网页面代理到选手本机” |
| 测试 | **Node.js 内置测试运行器**（`node --test`） | 规则层与接口的回归验证 |
| 节点级进度 | `/api/knowledge-progress` | 为六阶段 33 个可点击知识节点分别保存草稿、讲解、测验、错题、复习和通关状态 |
| 版本管理 | **Git** | 变更留痕 |

**本机演示**：Node.js 服务默认监听 `127.0.0.1:8787`，记录写入本机 SQLite；不配置远程模型时使用本地规则，离线仍可完成本机学习流程。**公网页面**使用独立 API 服务，数据位置与本机模式不同；启用模型复评时，讲解文本及必要上下文会发送给模型服务商。

本机模式面向可控演示；公网上线状态、数据存储和 AI 可用性须分别核验。

## ④ 技术方案

### 4.1 分层架构

系统自上而下分为七层，每层只做一件事：

| 层 | 职责 | 不做什么 |
| :--- | :--- | :--- |
| **页面层** | 学习工作台界面、路由与状态呈现 | 不含评分逻辑 |
| **3D / 可视化层** | 知识星海星图、课程路径呈现 | 不参与判定 |
| **内容层** | 课程总图为 10 章 · 57 个节点；另有 7 个核心模块级通关流程，六阶段中 33 个节点接入独立进度闭环 | 不把 57 个总节点都说成已独立验收 |
| **学习服务层** | 会话、计划、进度、通关状态的编排 | 不直接判分 |
| **记录层** | 按运行模式使用本机 SQLite、localStorage 或已配置的远程存储，记录模块与节点学习状态 | 数据所在位置随部署模式变化 |
| **讲解评价层** | 本地七项完整性筛查；配置模型后进行结构化复评 | **不判客观题** |
| **客观判题层** | 服务端预设标答独立判分 | **不涉及语义** |

**为什么要把"讲解评价层"和"客观判题层"拆成两层**——这是本方案唯一的架构性主张，第 ⑤ 章会详细论证：**两类判定的可信度来源不同，混在一层里就会互相污染。**

### 4.2 一个知识节点从学习到通关的数据流

1. 学习者进入六阶段路线中的一个知识节点，阅读课程内容并确认完成学习；
2. 节点页保存自己的讲解草稿，提交后先经过七项本地完整性筛查；
3. 需要 AI 复评且模型已配置时，服务端检索课程证据，将讲解与必要上下文发送给模型；
4. 模型返回引用编号后，服务端检查编号是否真实存在。**编号存在不等于引用内容支持该结论**，语义判断仍有误差；
5. 讲解通过后，学习者参加从现有题库中选择的 4 道客观题测验；服务端依据预设标答判分，达到 75% 才记录节点通关；
6. 系统按节点保存尝试、错题、复习与通关时间。语言模型不判客观题，也不直接写入通关。

这条独立闭环覆盖六阶段的 **33 个可点击节点**。它与 10 章、57 节点的课程总图，以及既有 7 个模块级通关流程是不同的统计口径。

### 4.3 三个设计选择与理由

**① 为什么用 Node.js 内置 HTTP，而不是 Web 框架。**
本项目的接口数量有限、形态固定，引入框架带来的抽象开销大于收益。内置 HTTP 让"服务能不能起来"这件事不依赖任何第三方包的安装状态——**演示现场少一个失败点。**

**② 为什么用 SQLite。**
在本机演示模式下，SQLite 无需独立数据库服务，程序重启后记录仍在，并可导出。静态模式使用浏览器 localStorage；公网页面按部署配置使用远程 API 与远程存储，不能把本机属性外推到所有模式。

**③ 为什么每条反馈都要标来源。**
如果一条反馈来自本地规则、却被学生误认为是模型判断，他就高估了这条反馈的可信度。**标注来源是让学生正确理解"这条反馈有多可信"的前提。**

### 4.4 失败与降级怎么处理

判断类功能最怕的不是失败，而是**失败后悄悄降级、用户却以为通过了**。本项目的处理是：

- 模型调用失败时，**明确降级并展示状态**，不自动判定讲解通过；
- **未配置模型时**，仍可用本地规则走完流程，**流程不中断**；
- 反馈中标注来源，学生能看出这一轮走的是哪条路径。

### 4.5 部署形态与数据边界

| 形态 | 页面与服务 | 记录位置 | 边界 |
| :--- | :--- | :--- | :--- |
| 本机服务 | 本机 Node.js，默认 `127.0.0.1:8787` | SQLite | 可在无远程模型时离线学习；模型复评不可用 |
| 静态回退 | 浏览器静态页面 | localStorage | 不提供跨设备同步；本地规则不是语义判断 |
| 公网演示 | Cloudflare Pages 页面经 `_worker.js` 转发到独立 Vercel API | 按后端配置；仓库记录使用 Turso | 公网可用性、AI 复评与数据持久化须各自实测 |
| Electron | 桌面入口 | 需按桌面包配置确认 | 与浏览器服务分别验收，分发资源及许可另行核查 |

线上模型复评会把讲解及必要上下文发送至模型服务商。任何演示材料都应说明当前运行的是本机、本地规则还是公网服务模式。

### 4.6 记录保存与隐私

本机服务模式把学习记录写入 SQLite；静态回退模式使用 localStorage。公网页面通过独立 API 服务处理请求，记录是否进入远程数据库取决于该服务配置。

记录可包括节点草稿、讲解反馈、测验历史、错题、复习状态与通关时间。模型未配置时，这些记录不会因此变成 AI 判断；启用远程模型时，学生讲解与必要上下文会离开设备发送给模型服务商。

**因此，本方案不承诺“所有数据永不出机”或“所有模式都可跨设备同步”。** 演示前应确认当前运行模式，并向使用者说明数据去向。

### 4.7 验收证据的适用范围

仓库保留了原模块级闭环的历史验收记录、后续页面检查和节点进度实现。历史记录只支持当时的测试条件，不能自动外推为当前线上服务状态。

新增的 33 节点能力以代码中的 `/api/knowledge-progress` 路由、前端节点工作流和 `tests/knowledge-progress.test.js` 为复核入口。**本方案不把测试文件存在写成测试已通过，也不以功能截图代替运行验收。** 交付前应在本次提交对应版本上重新运行验证，并记录实际结果。

## ⑤ AI 功能在作品中的核心作用

本章回答三个问题。**三个都必须回答，缺一个这套设计就不成立。**

### 5.1 第一问：没有模型时，产品还可以做什么

先把话说透：**如果没有语言模型，节点学习、七项完整性筛查、客观测验、错题复习与进度记录仍可运行。**

它仍然能工作——本地规则会告诉你"你没有举例子""你没有说明适用边界"，客观题照常判分，流程照常走完，**这正是本项目"未配置模型时流程不中断"的设计**。

但本地规则**不能可靠判断讲解在语义上是否正确**；系统会明确显示本轮使用的是本地规则，不把它包装成 AI 复评。

规则层能测的是"说了多少"：有没有足够内容、有没有例子、有没有提到边界。规则层**测不了"说的是不是真的"**。一个把术语全部堆齐、逻辑却完全说反的讲解，在规则层看来是满分答案。

启用模型时，AI 可以依据课程证据提供额外的结构化语义反馈；模型反馈仍可能出错，不能替代客观测验、教师审阅或效果研究。

### 5.2 第二问：启用模型后，AI 参与哪一步

本作品将模型复评作为**可选的讲解反馈**。未配置模型时，本地学习流程仍可继续，但语义层面的判断能力缺失。

**位置**：本地七项规则筛查符合调用条件后，服务端检索课程证据并将必要上下文交给模型复评。

**功能**：对机制、因果、例子和边界给出结构化反馈。默认本机哈希嵌入主要反映词面重合，不等于语义检索；服务端检查模型返回的引用编号是否存在，但该检查**不证明引用支持模型结论**。

**为什么规则层做不到**，这一点我们用**对抗性审计**测过，不是推测（项目自测，非第三方背书）：

| 对抗样本 | 结果 | 说明 |
| :--- | :--: | :--- |
| `naiveBot`：无机制、无例子、无边界的敷衍作答 | **0 / 140 全部被拦截** | 规则层对"说得太少"有效 |
| `grammarBot`：语法通顺、术语齐备、但语义空洞的作答 | **140 / 140 可穿透** | **规则层对"说得漂亮但不对"无效** |

这一对数字是本项目最重要的技术证据。`naiveBot 0/140` 证明了规则层的有效性边界——它能拦住敷衍；`grammarBot 140/140` 证明了规则层的**失效边界**——它拦不住套话。**140 次全部穿透，不是偶发，是结构性的。**

**结论**：规则层是完整性筛查。配置模型时，服务端 AI 复评可以补充语义反馈；没有模型或调用失败时，不应把本地规则说成语义判断。

**服务端边界**：客观判题与通关状态仍由确定性服务端规则控制。远程模型会接收必要的讲解文本与上下文；引用编号验证只确认编号存在，仍需人工判断引用是否支撑结论。

### 5.3 第三问：AI 的边界在哪——哪些判断不由 AI 做

这是本方案与"把大模型接进来做智能问答"最根本的区别。**我们把判定职责按可信度来源拆开，而不是让模型包办：**

| 判定内容 | 由谁判定 | 为什么 |
| :--- | :--- | :--- |
| **客观题答案对错** | **服务端预设标答** | 有唯一正确答案的场景不需要模型介入；标答可复核、可复现、成本为零 |
| **是否记录通关** | **服务端按双条件计算** | 通关是产品状态，必须由确定性逻辑写入 |
| **讲解的语义是否成立** | 可选 AI 复评提供参考反馈 | 可能误判；引用编号存在不等于引用支撑结论 |
| **讲解的完整性** | 本地规则（七项筛查） | 是启发式检查，不保证语义正确 |

**三条硬边界**：

1. **模型无权决定客观题答案。** 有标答的题，模型不参与。
2. **模型无权写入通关。** 模型只输出复评意见；是否通关由服务端按"讲解通过 + 客观测验 ≥ 75%"计算。
3. **模型不能成为唯一判据。** 讲解与测验两个条件**分别计算、互不代偿**——讲解写得再好也不能免测验，测验满分也不能免讲解。

内部对抗测试表明，完整模板可以穿过本地规则筛查（`grammarBot 140/140`）。这说明本地筛查不是语义判据；模型复评也不是确定性事实核验。

### 5.4 AI 复评的智能体流程

AI 复评不是一次单轮问答，而是一条有明确阶段的三步流程：

**① 接收请求**
服务端接收讲解提交，组装上下文：系统提示、学习任务、当前概念、课程摘要、学生原文。
前置条件是本地七项筛查已通过——**未通过的请求不会进入这一步**。

**② 检索与复评**
服务端从课程材料中检索证据，再由可选模型按预设维度生成结构化反馈。服务端核对引用编号是否存在，但不自动证明引用内容支持结论。
输出是**结构化的评价对象**（各维度结论 + 反馈文本），不是一段自由文本——这样才能把反馈映射回界面上的具体条目。

**③ 反馈结果**
服务端把复评意见与本地规则结果**合并**，返回给学习工作台：
- 每条反馈**标注来源**（本地规则 / AI 复评）；
- 若模型调用失败，**标记降级状态并展示**，**不自动判定讲解通过**；
- 学生据此修订讲解，再次提交，形成"讲 → 被指出缺口 → 改 → 再讲"的循环。

**这条流程与作品内其他模块的协同关系**：复评结论写入记录层，供错题复习与学习记录导出读取；通关状态则由客观判题层与学习服务层共同确定——**AI 的输出是输入之一，不是最终裁决。**

### 5.5 复评质量的自测

本项目用**双盲复评 21 组**做过一轮自测（项目自测，非第三方背书）：

| 指标 | 结果 |
| :--- | :--: |
| 准确率 | **90.5%** |
| 精确率 | **100%** |
| 假阳性 | **0** |

**假阳性为 0 这一项对本作品尤其重要**：它意味着在测试样本中，**没有出现"讲解其实不成立、却被判为通过"的情况**。对一个以"验收"为核心的产品来说，宁可漏判，也不能错判——错判会让整个验收机制失去意义。

需要说明：21 组是自建测试集，**不是第三方评测**，样本量也小，只能作为内部质量信号。

### 5.6 这套设计的代价

诚实记录三条边界（完整清单见第 ⑨ 章）：

1. **当前为原型阶段，尚无教育效果的因果数据。** 我们没有做前测 / 后测对照，不能声称"用了它成绩会提高"。
2. **本地讲解规则存在漏判**（`grammarBot 140/140` 已量化这一缺陷）；未配置模型时没有语义复评，配置模型后仍可能误判。
3. 自测样本量小，且本次问卷 **n=20 为探索性、非随机抽样**。

## ⑦ 使用说明：操作流程与交互指南

### 7.1 操作流程

**首次使用（演示一个知识节点）**

1. 开演前确认本机服务、访客档案与当前模型状态；不要把本地规则反馈说成 AI 复评。
2. 进入六阶段路线中的一个可独立记录节点；
3. 阅读并确认完成学习，提交自己的讲解；
4. 查看本地筛查或可选模型反馈，按缺口修订；
5. 讲解满足节点条件后开始 4 题测验；
6. 达到 **75%** 后，服务端记录该节点通关；否则回到错题复习；
7. 刷新页面确认本次节点状态恢复。模块级入口仍保留原诊断、计划和七模块通关流程。

**回访使用**

- 本机模式从工作台恢复本机记录；静态回退从浏览器恢复 localStorage；公网模式的记录按后端配置保存；
- 从错题复习进入待复习内容；
- 需要时可导出学习记录。

### 7.2 交互指南

| 状态 | 界面表现 | 用户该做什么 |
| :--- | :--- | :--- |
| 讲解内容不足 | 反馈指出具体缺哪一项（如"待补充：适用边界"） | 按提示补写对应部分，其余不用重写 |
| 讲解未通过本地筛查 | 直接返回结果，**不触发远程调用** | 修订后重新提交，反馈速度更快 |
| 讲解通过本地筛查，等待复评 | 显示等待状态 | 等待结果，无需重复点击 |
| **复评调用失败** | **明确显示降级状态与来源标注，不判定为通过** | 可稍后重试，或用本地规则结果继续修订 |
| **未配置模型** | 展示来源为"本地规则"，**流程不中断** | 仍可完成讲解与测验，仅语义层面把关缺失 |
| 测验未达标（< 75%） | 显示得分与达标线，标记该模块未通关 | 复习后重新测验 |
| 讲解通过但测验未达标 | 讲解项标为已通过，通关项标为未完成 | 只需补测验，不必重写讲解 |
| 记录已保存 | 无需操作 | 刷新或重开程序后进度仍在 |

### 7.3 离线与断网时的行为

- 在**本机 Node.js + SQLite**模式中，不依赖远程数据库即可继续本地规则筛查、客观测验与记录保存；未配置模型时不提供语义复评。
- 公网模式依赖远程 API 和所配置的数据库；网络断开时不能据此宣称流程仍完全可用。
- 若远程模型调用失败，界面应明确显示状态与来源；本地规则不能冒充 AI 语义判断。
- 开演前确认入口、记录位置、AI 是否配置以及失败后的演示分支。

**演示建议**：现场演示时可先展示正常运行流程，再断网展示降级处理——**"失败时它怎么表现"比"成功时它怎么表现"更能说明系统的可靠性设计。**

## ⑧ 应用前景与商业模式

> **本章的所有商业模式内容均为待验证假设，不是已实现的商业成绩。**
> 当前**没有已签客户、没有收入、没有真实用户留存、没有教师访谈、没有教育效果结论**。

### 8.1 应用前景：可推广的条件与当前限制

**可推广的条件**

1. **可从本机试点开始。** Node.js 与 SQLite 可用于单机演示；机构部署、远程数据存储与服务支持成本仍需评估。
2. **课程结构分层。** 总图为 10 章 · 57 节点；7 个核心模块保留模块级通关，另有六阶段 33 个知识节点实现独立进度。更换学科需要重新整理内容、判据与题库，不能仅靠替换文本。
3. **判据可复现。** 讲解评价与客观判题分离，客观题按标答判分，任何一次判定都可以被复核。

**当前限制（必须先说清）**

1. **原型阶段**，没有教育效果的因果数据；
2. **教师侧能力未交付**——班级视图与概念错因汇总属后续产品范围；
3. **本机原型不等于云部署**，也不等于跨设备账号与商用交付；
4. **第三方素材授权未完成**（见 8.4）。

### 8.2 商业路径：三层假设与验证顺序

以下分层是**待验证的假设与验证顺序**，不是已交付功能或已确认价格。

| 客户层 | 假设交付物 | 收费逻辑（**待验证**） | 关键前置条件 |
| :--- | :--- | :--- | :--- |
| **高校 B 端（主路径）** | 7 个核心模块的课程实践包、讲解验收流程、基础学习记录；后续再评估教师班级视图与概念错因汇总 | 按院系或课程授权的年费制，**避免先按学生人头计费** | 访谈任课教师与预算负责人；用小范围课程试点验证部署、备课与支持工时 |
| **企业 B 端（次路径）** | 定制课程任务、私有部署、企业内部知识库 RAG 实验环境（规划） | 项目实施费 + 年维护费，价格由部署、内容审校与支持范围决定 | 先确认数据隔离、部署、知识库接入与服务等级要求；**当前原型尚未交付这些能力** |
| **C 端长尾** | 开源代码核心、本地练习、内容包或部署支持（规划） | 免费核心 + 付费内容/部署/支持 | 核对模型提供商条款、支付与支持成本 |

**主路径为什么是 B 端而不是 C 端**：本作品的核心价值是"验收"，而验收的价值要靠**课程或班级的约束力**才能兑现。个人用户可以选择不验收，课程场景不能——**约束力来自课程，不来自产品本身。**

### 8.3 成本量级：情景估算，不是报价

当前**没有 API 用量记录或真实账单**，以下仅用于判断量级：

| 情景 | 调用假设 | 结果解释 |
| :--- | :--- | :--- |
| 本地练习 | 不调用远程模型 | **无远程调用费**，但仍有维护、内容审校与支持成本 |
| 远程复评示例 | 每次约 500 token 输入 + 200 token 输出 | 当前代码发送的上下文包含系统提示、任务、概念、课程摘要与学生文本，**token 数尚未实测**；`max_tokens` 上限为 900，不能把 200 当作已观测值 |
| 节点量级示例 | 33 个独立进度节点 × 每节点 2 次可选模型复评 = 66 次 | 33 是当前六阶段闭环节点数；该算式只是上限情景，不是实际调用量，也不含模块级流程 |

举例说明量级：**若**经账单核实单次调用成本为 ¥0.001，则 66 次约为 **¥0.066**。
**这个数字只说明模型调用的一个情景量级**，不能据此宣称"总边际成本低于某值"——完整单位成本还应加入服务资源、内容审校工时、教师支持、支付费用、授权与部署维护。
